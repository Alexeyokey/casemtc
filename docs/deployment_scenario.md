# Предлагаемый сценарий внедрения и бизнес-метрики (S5)

Раздел для защиты (блок Жени: внедрение, заявки, надёжность). Это **предложение**: реальной интеграции с CRM, почтой или сайтом МТС в прототипе нет, и мы её не заявляем.

## 1. Как встраивается

1. **Виджет на сайте/лендинге продукта.** Web-чат (U1–U5) подключается одним `<script>` или `<iframe>` и общается с backend по `/api/v1`. Сессия живёт во вкладке (токен вкладки), кнопка «Новый диалог» закрывает прежнюю.
2. **Backend** — один контейнер (`docker compose`) с SQLite на томе. Ядро консультации подменяется переменной `CONSULTATION_ENGINE` без изменения API.
3. **Заявка сегодня:** запись в БД, файл `<lead_id>.md` и список в `/api/v1/archive/leads`. Менеджер или проверяющий читает их по токену архива.
4. **Заявка завтра (не реализовано):** добавить отправителя-«outbox». После `saved` событие кладётся в очередь, отдельный воркер отправляет его в CRM (amoCRM/Bitrix24/внутренняя) и пишет статус `delivered/failed` с повторами. До подтверждённой доставки интерфейс продолжает писать только «сохранена». Контракт `LeadView.delivery` уже отделяет «сохранена» от «доставлена».
5. **Масштабирование:** SQLite → Postgres, блокировка хода → advisory lock/Redis, несколько воркеров. Это нужно только при реальной нагрузке, по замерам.

## 2. Ценность заявки для менеджера

- Телефон проверен по формату и нормализован в E.164.
- Резюме разделяет «известно со слов клиента», «предположения», «обсуждённые решения» и «неизвестно». Менеджер видит, что уточнить в первом звонке, и не получает выдуманных бюджета или компании.
- Полная история доступна отдельно, если нужен контекст.

## 3. Метрики, которые можно посчитать по архиву

Все считаются по архиву (`exports/sessions.jsonl`) без внешних систем:

| Метрика | Как считается |
|---|---|
| Доля диалогов с сохранённой заявкой | `lead.status == saved` / все сессии с ≥1 ходом |
| Доля «готовых, но не сохранённых» | Телефон есть, `saved` нет — сигнал UX-проблемы формы |
| Доля отказов от контактов | `client_context.contact_status == refused` |
| Полнота заявки | Доля заявок с ФИО/компанией помимо телефона |
| Доля эскалаций и отказов по компетенции | `action in (escalate, out_of_scope)` по трассам |
| Ошибки и задержка | `turns.status == failed`, p50/p95 из `scripts/bench_latency.py` и трасс |

**Чего не утверждаем:** прироста конверсии, экономии времени менеджеров в часах, выручки. Для этого нужен A/B-тест на реальном трафике после внедрения, и мы предлагаем его как следующий шаг.

## 4. Эксплуатационные риски

| Риск | Что сделано | Что ещё нужно |
|---|---|---|
| Персональные данные в БД и логах | Маскирование в логах и трассах, архив по токену, `data/` вне Git | Срок хранения, шифрование тома, согласие на обработку ПДн в виджете |
| Падение процесса посреди ответа | Прерванные ходы → `failed`, повтор без дублей | Мониторинг доли `failed` |
| Утечка ключей API | Маскирование `Authorization`/`sk-…`/`api_key` | Секреты только через env/secret store |
| Медленная модель | Замер p50/p95, SSE-событие `accepted` для индикатора | Оптимизация по измерениям (R4/C*) |
| Ложные обещания клиенту | Статус `stored_only`, резюме без выдумок | Контроль фактов в ответах (C4) |
