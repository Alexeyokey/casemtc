# I5 · Замеры и приёмка EnergyTool

## Воспроизводимая локальная проверка

Из корня репозитория установите зависимости из `requirements.lock` и запустите тесты и замер. `artifacts/` подходит для локальных отчётов и ZIP.

```sh
mkdir -p artifacts
python3 -B -m unittest discover -s tests -v
python3 -B scripts/benchmark_submission.py \
  --artifact artifacts/energytool-runtime.zip \
  --output artifacts/energytool-benchmark.json
```

Замер использует синтетические документы, вопросы и прокси на `127.0.0.1`. Он собирает `runtime` ZIP, запускает его в чистом каталоге и записывает SHA коммита и архива, число вызовов, время построения индекса, холодный запуск и p50/p95 повторных запросов. Сохраняйте отчёт вместе с проверенным ZIP. Положительный балл судьи и время на платформе подтверждаются отдельным прогоном.

Для проверки веба используйте команды из [I4](I4_DOCKER.md). Проверьте заявку с валидным тестовым телефоном, отказ от контактов, повтор сохранения, устаревшее резюме, новый диалог и сохранность истории после пересоздания контейнера. Для общей приёмки сравните вывод по учёту и распознаванию фото в вебе и CSV. Отдельно прогоните пару сценариев потерь с дневной и ночной разбивкой и без неё. [Критерии команды](REQUIREMENTS.md#финальная-проверка-команды)

Синтетические сценарии проверяют передачу истории, источников и действий между компонентами. После нескольких коротких реплик текущий поиск по трём последним сообщениям пользователя может потерять раннюю тему. При приёмке C2 отдельно проверить запрос обратной связи в таком диалоге. Резюме должно сохранить сведения о задаче. [Сценарии](../tests/fixtures/energytool_acceptance.json) · [C2 #10](https://github.com/Alexeyokey/casemtc/issues/10)

## Платформенный прогон и материалы сдачи

1. После сквозной приёмки собрать `runtime` ZIP от согласованного SHA. Зафиксировать SHA-256 архива и список его файлов. Сверить действующий регламент и доступ к кабинету команды. Выданная база подаётся отдельно.
2. На прокси организаторов проверить генерацию, эмбеддинги и реранкер. Записать фактические форматы, параметры reasoning и таймауты. Подготовить один пробный сабмит с учётом лимита пяти попыток в сутки и 20 минут на прогон.
3. В отчёте о сабмите заполнить дату по Москве, ID попытки, SHA коммита и ZIP, профиль, длительность, число вызовов и фактический балл. Для готового индекса отдельно сохранить подтверждение загрузки на платформе. При отсутствии подтверждения использовать `runtime`.
4. Собрать PDF после проверки блоков владельцами. На первом слайде дать порядок запуска и проверки, ссылку на репозиторий и доступный адрес UI при наличии. Далее показать сценарий клиента, поиск и проверку фактов, контракт, замеры и итог платформы. Проверить доступ жюри и совпадение SHA материалов.

Для журнала платформы храните поля `submission_id`, `commit_sha`, `artifact_sha256`, `profile`, `elapsed_ms`, `api_calls`, `judge_score` и `receipt`. До официального запуска поля результата остаются пустыми. [Задача I5](https://github.com/Alexeyokey/casemtc/issues/26)
